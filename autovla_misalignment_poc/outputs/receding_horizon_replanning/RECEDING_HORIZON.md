# 재계획(receding horizon)은 token feedback 발산을 끊는가 — 로그 관측 위의 pseudo closed loop

**답: 자주 재계획하면 A− 장면의 5 s 실패가 크게 줄지만(59.6% → 23.5%), 그 이득의 일부는 로그 관측이 실제 경로를 알려 주는 누출에서 옵니다. 자기 실행 상태를 되먹이면 8 s 오차가 로그 상태 대비 A− +5.5 m, A+ +2.5 m 커지는 상태 수준의 feedback이 새로 생기고, 재계획 안에서 이전 계획으로 안정화하면 A−의 회복을 오히려 막습니다.**

- 스크립트: `scripts/receding_horizon_replanning.py` (GPU 1), `scripts/analyze_receding_horizon.py`, 공용 `scripts/_planner.py`, frame 준비 `scripts/build_frame_scenes.py`
- 데이터: equal-distance 집합의 장면 208개(A− 52, A+ 156), 8 s 로그가 있는 장면 200개(A− 50, A+ 150). perturbation 없이 natural 경로로 계획.
- 실행: 2026-09-29, RTX 5090, torch 2.8.0+cu128, T = 0.01, seed 0, 계획 6943개, 125분. CoT stub으로 빠진 계획 0개.

## 1. 질문

실험 10은 feedback 안정화가 재발산을 늦출 뿐 막지 못하며, 5 s 이후는 분포 밖이라 검증할 수 없다고 남겼습니다. 실제 주행 스택은 주기적으로 재계획합니다. 재계획이 (a) token feedback 발산을 끊는지, (b) 안정화와 어떻게 상호작용하는지를 봅니다.

## 2. 설계

f0에서 계획하고 처음 m개 토큰(m × 0.5 s)만 실행한 뒤, **로그의 f0 + m frame 카메라**로 다시 계획하는 것을 8 s까지 반복하고, 실행된 조각을 이어 붙여 로그 궤적과 비교합니다.

| 조건 | ego 상태 입력 (prompt의 속도·가속도 크기) | 비고 |
|---|---|---|
| `ol` | – | 단일 계획 10 토큰 (5 s) |
| `m{2,4,8}_log` | 재계획 frame의 로그 상태 | 순수 open-loop 재계획. **실제로 일어난 속도를 받으므로 oracle 상한** |
| `m{2,4,8}_exec` | 로그 상태 + (실행 경로 속도 − 로그 경로 속도), 최근 0.5 s 유한차분 | pseudo closed loop |
| `m{2,4,8}_exec_prev` | exec와 같음 + 재계획 r ≥ 1에서 context 위치 0..w−1 := 이전 계획을 m칸 민 토큰 (w = min(3, m−1)) | GT·oracle 시점 없음 |

카메라는 모든 조건에서 로그를 따릅니다. 실행 경로가 로그와 어긋난 크기는 재계획마다 기록했습니다(A− exec 평균 3.2–4.5 m, 최대 7 m; A+ 1.2–1.7 m).

실패 = P/R/A 5 s 판정 A− ∧ FDE5 > 3 m (증폭 정의와 동일). CI는 log cluster bootstrap 95%.

## 4. 해석

1. **재계획은 token feedback 사슬을 끊습니다.** 2–4 step마다 새 관측으로 다시 계획하면, 실행 상태를 되먹이는 조건에서도 A− 5 s 실패가 59.6% → 23.5%로 줄어듭니다. 8 step(4 s) 간격은 효과가 없습니다(59.6%). 한 계획 안에서 실행되는 autoregressive 전이가 짧을수록, 실험 7–10의 직전 토큰 feedback이 자랄 시간이 없습니다.
2. **그러나 이 이득은 상한 쪽으로 편향돼 있습니다.** 재계획 때 보는 카메라는 실제로 간 경로(로그)의 관측이라, 실행 경로가 평균 3–4.5 m 벗어나 있어도 모델은 올바른 위치의 장면을 봅니다. 속도까지 로그에서 받으면(`log`) 실패가 0%가 되는 것이 그 누출의 크기를 보여 줍니다. 진짜 closed loop에서는 관측도 벗어난 위치를 보여 주므로 이득이 이보다 작을 수 있습니다.
3. **자기 상태를 되먹이는 것 자체가 새 feedback 경로입니다.** 같은 카메라에서 속도만 실행 경로로 바꿔도 8 s 오차가 A− +5.5 m, A+ +2.5 m 커지고, A+에서는 자주 재계획할수록 단일 계획보다 오히려 나빠집니다(m2 +0.41 m). 토큰 수준 feedback(실험 7–10)이 재계획으로 끊기는 대신, 계획 사이에서 속도를 통한 상태 수준 feedback이 생깁니다.
4. **재계획 안에서 이전 계획으로 묶으면 회복을 막습니다.** 실험 12에서 도움이 된 이전 계획 참조가 여기서는 A− 8 s 오차를 +1.6–3.2 m 늘리고 실패 감소를 −35%p → −14%p(m4)로 줄입니다. 실험 12의 이전 계획은 perturbation과 무관한 독립 참조였지만, 재계획에서의 이전 계획은 **지금 틀어지고 있는 바로 그 계획**이라 새 관측으로 다시 맞추려는 것을 틀린 쪽에 묶습니다. A+에서는 약간 도움이 됩니다(−0.5 m, CI가 0에 걸침). 일관성(consistency)과 교정(correction)이 충돌하며, 어느 쪽이 이기는지는 이전 계획이 맞았는지에 달려 있습니다.

## 5. 한계

- **pseudo closed loop**: 카메라가 로그를 따르므로 관측을 통한 누출이 있습니다. 진짜 평가는 NAVSIM v2 pseudo-simulation이나 nuPlan 시뮬레이터처럼 실행 경로에 따라 관측을 만드는 환경이 필요합니다.
- 상태 입력은 prompt의 속도·가속도 크기뿐입니다(원 모델의 입력이 그것뿐). 실행 상태는 로그 순간값에 유한차분 보정을 더해 근사했습니다.
- `Planner`는 stub을 새로 생성하므로 저장된 natural 계획과 토큰이 항상 같지는 않습니다. 이 때문에 `ol`의 A− 실패율이 100%가 아니라 59.6%입니다(같은 실행 안의 비교이므로 대조는 유효).
- A− 52 장면, 단일 seed, T = 0.01.
