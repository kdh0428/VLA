## 2. 완료된 일과 이번 작업 범위

완료된 증거를 재실행하지 않는다.
- AutoVLA 주행 open-loop 개입, 운동 반응, 기존 PDMS 분석.
- VLA-0 149개 유효 관측/30개 task의 within-call pilot.
- VLA-0 4개 task–state unit, 각 48-step의 짧은 폐루프 실행.
- SpatialVLA 기존 cross-step task-success 분석.

이번 실행의 질문은 **같은 관측·같은 출력 prefix에서, conditioning의 최근 행동과 이전 행동을 바꿀 때 SpatialVLA의 후속 행동 반응이 어떻게 다른가**이다. 새 task-success 실험이나 장기 폐루프 실험은 범위에 포함하지 않는다. 자연 rollout으로 관측을 수집하는 것은 허용한다.

기존 프로젝트는 `/root/VLA`에 있을 것으로 예상되지만 실제 위치·AGENTS.md·환경을 확인하라. 기존 작업을 보존하는 별도 branch/worktree 또는 새 실험 디렉터리를 사용하라. 기존 패키지와 실행 당시 코드를 덮어쓰지 않는다.

이 지시의 구현·검증·예산 내 pilot·분석은 연속해서 수행하라. 각 단계 보고만 하고 중단하거나 같은 실행 허가를 다시 묻지 않는다. 기술적 중단 조건이나 예산 한계에 도달하면 실제로 얻은 결과와 재개 명령을 제출한다.

## 3. 시간 예산과 실행 순서

- 모델 GPU가 할당된 상태의 누적 wall time으로 계측한다. 실패·재시도와 관측 수집도 포함한다.
- 단일 GPU 기준 feasibility는 최대 30분, 통과 후 pilot는 추가 최대 120분, 합계 최대 150 model-GPU minutes.
- 여러 GPU를 쓰면 장치별 할당 시간을 합산한다. 기존 작업을 중단하거나 GPU를 독점하지 않는다.
- latency를 실제 측정하고 예정 표본 수·예상 종료 시간을 기록한다. 위 시간은 상한이며 속도 보장이 아니다.
- GPU 실행 전 CPU 점검, feasibility, pilot 순서로 진행한다. 캐시 문제의 원인 추적을 무한히 반복하지 않는다.

## 4. 공식 경로와 로컬 코드 확인

대상은 우선 기존 환경의 `IPEC-COMMUNITY/spatialvla-4b-224-sft-fractal`이다. 정확한 로컬 checkpoint revision, processor/model/tokenizer 코드와 statistics를 고정하라.

공식 공개 설정에는 `action_chunk_size: 4`가 있다. 공식 processor 예시는 한 행동을 translation/rotation/gripper의 3개 token으로 복호화한다. 이것은 설계 근거이며 로컬 개입 경로 검증을 대신하지 않는다.

다음을 코드와 실제 출력으로 확인해 간결한 표로 남겨라.
- 실제 기반 모델, chunk 길이, 행동별 token 개수·순서·허용 ID 범위.
- 이미지·텍스트 전처리, intrinsic/depth 등 모델 입력, prompt 및 action 경계.
- action normalization/unnormalization, 6개 운동 성분과 gripper의 순서·의미.
- 공식 generation defaults와 실제 사용 설정: cache, dtype, attention, EOS, max_new_tokens, repetition penalty, logits processor.
- 원시 출력의 길이, 잘못된 token type, 조기 종료, parser padding/truncation 처리.
- 모델이 4개 행동을 실제 autoregressive 순서로 생성하는지.

**PaliGemma 계열의 prompt/image attention과 생성 action의 attention 경계를 보존하라.** 편의를 위해 action prefix를 새 양방향 prompt로 취급하지 않는다. token_type_ids, attention_mask, position/cache 위치를 공식 생성 경로와 맞춰라.

확인되지 않은 최신 library로 전체 환경을 교체하지 말고 기존 검증 환경을 우선 재사용하라. 실행 전 fingerprint에 checkpoint/config/code SHA, Git commit 및 dirty diff, Python/package/CUDA, GPU, seed를 기록하라.

## 5. 개입 정의: 출력된 행동과 conditioning을 구분

이 절의 행동 번호는 **1부터 시작**한다. 실제 코드의 zero-based index 대응표도 저장하라.

자연 chunk를 `a1, a2, a3, a4`로 표기한다. 처음 두 행동의 원시 token 6개를 경계로 삼는다.
- 관측·instruction은 모든 arm에서 같다.
- **출력 기록의 a1,a2는 자연 행동 그대로 고정**한다.
- 후속 행동 a3,a4를 생성할 때 모델에 제공하는 conditioning의 a1 또는 a2만 바꾼다.
- 바뀐 conditioning을 실제로 실행된 prefix처럼 기록하지 않는다.
- 이 실험에서 개입 arm을 환경에 실행하지 않는다.

| Arm | conditioning a1 | conditioning a2 | 비교 대상 |
| --- | --- | --- | --- |
| N | 자연 | 자연 | 공식 자연 생성 결과 |
| R | 자연 self-patch | 자연 self-patch | 개입 구현으로 재생성한 a3,a4 |
| O | donor의 a1 | 자연 | 이전 위치 개입 |
| L | 자연 | donor의 a2 | 최근 위치 개입 |
| OL | donor의 a1 | donor의 a2 | 두 위치 개입, 보조 분석 |

한 행동의 3-token 묶음을 정확한 위치에 교체하라. 이하 donor 규칙에서는 gripper 값을 자연값과 같게 제한하므로 핵심 비교는 운동 성분의 문맥 변경이다. 특수 token이나 EOS를 묶음에 포함하지 않는다.

N/R 및 L/O/OL은 donor sampling과 독립된 RNG 상태를 사용한다. 본 생성·강제 재생성은 동일한 공식 deterministic 평가 설정을 사용하며, donor만 별도로 sampling한다.

## 6. Feasibility: self-patch부터 확인

결과를 보지 않고 고정한 별도 validation panel에서 12개 유효 자연 관측을 사용하라. 최대 24개 후보를 미리 manifest에 지정하고, 자연 출력 유효성만으로 앞에서부터 12개를 취한다. 후보·제외 이유를 모두 기록하고 pilot과 물리 layout을 분리한다.

검사:
1. 공식 자연 경로와 adapter의 입력·자연 출력 일치를 확인한다.
2. R self-patch의 a3,a4 원시 token identity가 **12/12**인지 확인한다.
3. 최종 복호화 행동도 일치하는지 확인하고, 같은 조건에서 측정 가능한 logit 최대 차이와 argmax 불일치를 기록한다.
4. 교체 index, 출력 prefix 불변, action type 유효성, native EOS/종료 정책 보존을 확인한다.
5. padding/truncation이나 token 문자열 재인코딩이 우연히 불일치를 숨기지 않는지 확인한다.

원시 action token 12개로 이루어진 구간이 유효하면 된다. 공식 경로의 정상적인 후행 EOS·특수 token을 임의로 실패 처리하지 않는다. 반대로 짧은 출력을 zero padding해 유효한 chunk로 간주하지 않는다.

R이 불일치하면 캐시·mask·위치·logits processor를 확인하고 예산 내에서 최소 수정하라. 수정 이유와 전후 결과를 보존한다. 같은 token-by-token replay가 필요하면 모든 arm에 일관되게 사용한다. 수치 정밀도가 원인이라는 설명은 근거가 있을 때만 한다.

12개 유효 관측을 확보하지 못하거나 R identity를 만족하지 못하면 feasibility STOP이다. 효과의 크기나 부호는 STOP 조건이 아니다.

## 7. Pilot 표본과 donor 규칙을 사전 고정

Feasibility 통과 후, intervention suffix 결과를 만들기 **전에** PROTOCOL과 manifest를 저장하고 Git commit 또는 SHA로 고정하라.

표본:
- 기존에 정상 작동한 Google-robot coke / move_near 두 task를 기본 panel로 사용한다. 정확한 task ID와 환경 설정을 기재한다.
- task별 최대 25개의 서로 다른 물리 layout/reset state를 사용한다. 사용 가능한 후보를 안정적인 ID/hash 순으로 정하고 validation과 겹치는 layout을 제외한다.
- layout별 자연 policy **generation call index 0,4,8**의 관측을 최대 3개 수집한다. environment step 번호와 구분해 함께 기록한다.
- 사전 고정한 episode 종료·수집 실패 규칙을 따르며, 종료 뒤 관측을 복제하지 않는다.
- 총 최대 150관측이다. 기존 move_near에 10개 layout만 있으면 그대로 쓰고 실제 수를 보고한다. seed나 frame을 늘려 새 layout으로 세지 않는다.
- 신규 물리 state인지, 기존 실험 state의 재사용인지 해시와 생성 규칙으로 구분한다.
- 예산에 맞지 않으면 측정 latency만으로 더 작은 균형 panel을 먼저 고정한다. 부호·p값·구간을 보고 표본 수를 바꾸지 않는다.

Donor:
1. 같은 관측과 instruction에서 독립 seed로 4개의 전체 source chunk를 sampling한다. 기본 `do_sample=True, temperature=0.7, top_p=1.0, top_k=0`을 사용한다. 공식 경로의 지원 여부를 확인하고 불가하면 결과를 보기 전에 지원 가능한 설정을 고정·기록한다.
2. source index 순으로 처음 나오는 **joint-valid chunk 하나**를 O/L/OL에 공통 사용한다.
3. joint-valid란 a1,a2의 token type이 유효하고, 각 위치에서 자연 행동과 gripper 값이 같고, 아래 6D 거리 d_O,d_L이 모두 0보다 큰 경우다.
4. 4개 모두 실패하면 SOURCE_MISSING이다. 추가 sampling이나 다른 seed 탐색으로 채우지 않는다.
5. source 후보 전체, 선택 index, 제외 이유, d_O,d_L과 거리 비율을 저장한다. donor를 continuation 반응 크기에 따라 선택하지 않는다.

Pilot의 모든 관측에서 N/R을 확인한다. R 불일치를 발견하면 해당 실행의 해석을 멈추고 기술 문제를 분리한다. 개별 실패를 조용히 제거해 효과 표만 완성하지 않는다.

## 8. 거리·분석 정의

공식 action tokenizer가 복호화한 **unnormalization 전의 6개 연속 운동 성분**을 u로 둔다. 축 순서와 값 범위를 먼저 확인하라. 그리퍼는 본 거리에서 제외하고 별도 보고한다.

관측 i에서:
- `D_i(X,Y) = (1/12) × sum_{t=3,4} sum_{d=1..6} |u_X[i,t,d] - u_Y[i,t,d]|`
- `E_L = D(L,R)`, `E_O = D(O,R)`, `Delta = E_L - E_O`.
- `d_O = mean_d |u_source[a1,d] - u_N[a1,d]|`.
- `d_L = mean_d |u_source[a2,d] - u_N[a2,d]|`.
- 거리 매칭 조건은 `0.8 <= d_L/d_O <= 1.25`이다.

**주 분석:** 사전 고정한 거리 매칭 조건을 만족하는 paired 관측의 Delta.  
**보조 분석:** 모든 joint-valid 관측의 Delta, task별 결과, a3/a4별 반응, translation/rotation별 반응, gripper 변화율, donor 거리와 반응의 관계.

거리 정의의 한계도 적어라. 정규화 Euler 성분의 절대 차이는 회전의 물리적 geodesic 거리와 다르다. native action 명세로 물리 회전을 계산할 수 있으면 보조 지표를 사전 정의하되, 주 지표를 결과에 따라 바꾸지 않는다.

- 공간 token ID의 차이를 행동 거리로 쓰지 않는다.
- 정규화 command 차이를 meter나 실제 EE 이동으로 부르지 않는다.
- `D(OL,L)`을 직접 계산한다. 이것은 `|E_OL-E_L|` 또는 `|mean(E_OL)-mean(E_L)|`과 다르다.
- signed interaction을 보조 보고한다면 `J=E_OL-E_O-E_L`로 명시한다. J가 0 근처라는 이유로 동등성·older 무효과·벡터 가산성을 주장하지 않는다.

집계와 구간:
- task 안에서 layout별 관측을 먼저 평균하고 layout에 같은 가중치를 준다. 그 다음 두 task 평균에 같은 가중치를 준다.
- task를 고정한 층으로 두고 layout 전체를 resample하는 bootstrap 10,000회, seed 20261022, 95% 구간을 사용한다. 같은 layout의 여러 관측은 함께 묶는다.
- 이 구간은 **두 task 조건부 layout 변동**에 대한 탐색적 구간이다. 2개 task로 새로운 task 모집단에 대한 일반화를 검증했다고 쓰지 않는다.
- task별 유효 layout 수를 함께 표기한다. 한 task에서 매칭 관측이 없으면 두-task 주 추정치는 NA이며 다른 task만으로 대체하지 않는다. layout이 1개 이하인 층의 추론 구간은 NA로 둔다.
- 적은 layout의 bootstrap 구간을 강한 확증으로 해석하지 않는다.
- missing/invalid/no-op와 zero response를 구분하고, 전체 후보에서 분석 표본까지 분모를 공개한다.
- 주 분석에서 L>O, L≈O, L<O 모두 그대로 제출한다. 성공 조건을 유의성이나 원하는 부호에 두지 않는다.

- 그림 PDF/PNG와 plotting source: task별 L/O와 paired Delta, a3/a4 반응, donor 거리 대비 반응. 결과를 확인한 뒤 고른 사례 그림은 illustrative라고 표시한다.

원시 값에서 표·그림을 재계산하고 분모와 단위를 점검하라. 숫자 문자열이 문서에 있는지만 검사하지 않는다. CPU verifier는 GPU·시뮬레이터를 호출하지 않고 raw 기록으로 결과를 복원할 수 있어야 한다.

원고 v02는 보존하고, 논문 반영 후보 문장·표와 위치를 CLAIM_DELTA에 제안하라. 전체 8쪽 원고를 다시 편집하는 일은 이번 실행 검증 이후에 판단한다.

## 10. 해석과 중단 보고

이 실험은 **다른 기반 모델 계열의 같은 호출 내 문맥 반응**을 추가한다. 성능 개선법, 주행 정책의 closed-loop 효용, 광범위한 task 일반화까지 자동으로 확립하지 않는다. AutoVLA 상위 군집 수 문제와 SpatialVLA 기존 두-task 평균 ±10 pp의 범위도 바뀌지 않는다.

- 유효 경로 + 매칭 후 L>O: 해당 checkpoint/task panel에서 위치 반응의 재현 근거.
- 유효 경로 + 작거나 반대인 효과: 위치 반응의 모델·표현·문맥 의존성을 보여주는 결과. 불리한 결과를 숨기지 않는다.
- 경로 미검증: 새 backbone 결과를 주장하지 않는다. 정확한 실패 위치와 확보한 raw 자료를 제출한다.
- 실행하지 못함: 구현 완료 / CPU 확인 / GPU 미실행을 명확히 구별한다. 실행 로그나 숫자를 추정해 채우지 않는다.

마지막 응답에는 실제 수행 범위, 12-case parity, 주 추정치와 조건부 구간, task/layout/관측 분모, GPU 시간, ZIP 경로와 다음 작업 하나를 간단히 적어라. 새로운 대규모 실행을 자동으로 시작하지 않는다.
